# C 代码规范检查

每轮用户消息后判断适用性：本轮开始编写代码前应用本技能，完成后检查本轮实际编写的代码。只阅读、讨论、审查而未编写代码时跳过，不输出无意义的检查报告。非 C 代码不套用 C 专用规则。

## 规范与边界

以 MISRA C:2012 和 BARR-C:2018 为基线。BARR 的排版和注释规定由以下定制要求覆盖：采用 K&R 排版，所有新增和修改的注释必须用中文描述，并使用 Doxygen 风格。Doxygen 标签、参数名、标识符和必要的协议原文可以保留原文。

遵守项目 AGENTS.md、编码、换行、工具链和接口约束。发现无法同时满足的规则时明确指出冲突及具体偏差理由，不默默宣称合规，不扩大为全库重排。第三方库、生成代码及未触及的遗留问题不擅自重写。

## 编写与自检

- 审查本轮差异及相关调用关系；重点核查整数提升与基本类型、符号性、窄化转换、溢出、移位范围、数组与指针边界、对象生命周期、初始化、空指针、求值顺序和副作用。
- 核查控制流、完整条件分支、switch 分支及明确终止、返回值与错误处理、资源释放、宏参数与括号、声明及链接可见性；嵌入式代码额外核查 volatile、ISR 共享数据、原子性、寄存器访问和阻塞约束。volatile 不能替代同步。
- 避免未定义、未指定及未经记录的实现定义行为；不得通过不安全强转、屏蔽警告来掩盖问题。必需的平台扩展或硬件操作记录理由、影响和验证方法。
- K&R：函数定义的左花括号单独一行；if、for、while、switch 等控制语句的左花括号放在语句行末；else 与前一右花括号同行。控制语句的主体始终使用花括号。采用一致缩进，项目未规定时使用 4 个空格。
- 注释写作范围限于本轮创建或修改的内容，且描述必须有已阅读代码和已知上下文支持，不猜测未了解的职责或约束。局部修改只为对应逻辑补充必要说明，并同步受改动影响的已有注释，不因此补齐或重写整个文件、函数的注释。文件头和函数头描述完整对象的整体职责，不得将本次局部功能提升为整体用途；上下文不足时，不补写整体描述。
- 新建 .c 和 .h 须有中文 Doxygen 文件头（@file、@brief）。新增函数定义须有中文 Doxygen 函数头：@brief、每个参数的 @param（适用时注明 in/out）、@return；无返回值明确写 @return 无。新增的头文件公开函数声明同样需要接口注释，说明已知的前置条件和调用约束；新增或修改的宏、类型、成员和全局对象按其语义及上述范围补充必要的中文 Doxygen 注释。所有多行 Doxygen 注释（文件头、函数头等）的首行只写 `/**`，中间各行以 ` * ` 开头，末行 ` */` 单独成行。
- 为本轮创建或修改的函数内部逻辑添加必要的中文注释，说明主要处理步骤、重要状态转换、边界条件、失败处理和资源清理的目的及约束；不逐行翻译语句，不编造用途。内部说明采用 /** ... */，成员可用 /**< ... */。注释贴近对应代码且与实际行为同步。
- 优先修复自己引入的问题，再运行适用的构建、静态分析及有意义的测试。使用现有 MISRA 检查器及工程配置；未安装检查器或没有标准全文时明确说明覆盖范围，不捏造规则号，不把人工检查、编译通过等同于完整标准认证。

完成时简要报告修改范围、实际执行的验证及残留偏差。没有证据不得声称完整 MISRA/BARR 合规；需要正式合规声明时须使用获授权的标准全文、合规计划、工具报告与偏差记录。
